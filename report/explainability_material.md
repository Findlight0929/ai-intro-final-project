# 可解释性模块报告素材

## 模块目标

本项目的可解释性模块用于在模型给出谣言分类结果后，进一步输出简洁、可读、可复核的判断依据。模块不直接判断文本事实真伪，而是解释模型为什么更倾向于将输入文本判为 `rumor` 或 `non-rumor`。

## 规则化解释方案

解释模块从以下角度抽取文本信号：

1. **夸张或煽动性表达**：例如 `breaking`、`urgent`、`shocking`、`must see` 等词语。这类表达常见于吸引转发或制造紧迫感的社交媒体文本。
2. **绝对化词语**：例如 `always`、`never`、`everyone`、`clearly`、`definitely`、`100%` 等词语。这类词可能增加文本的断言强度，但不一定提供证据。
3. **缺少可靠来源**：检查文本中是否出现 `according to`、`official`、`confirmed`、`statement`、`reported` 等来源或报道线索。若缺少这些线索，解释中会提示“缺少明确可核验来源”。
4. **常见谣言表达模式**：例如 `cover-up`、`hiding`、`leaked`、`secret`、`hoax`、`smear campaign` 等，这类表达常与阴谋、泄露、隐瞒等叙事有关。
5. **不确定或推测性表达**：例如 `maybe`、`might`、`could`、`apparently`、`allegedly`、`unconfirmed` 等，用于提示文本可能基于推测而非确定证据。
6. **社交媒体上下文**：识别链接、话题标签和疑问句等信号，提醒读者需要结合外部证据进一步核验。

## 与分类模型的结合方式

分类模型首先输出预测标签：

- `0`：非谣言
- `1`：谣言

解释模块随后根据预测标签组织不同的解释文本：

- 当预测为谣言时，优先说明文本中的高风险信号，例如夸张表达、绝对化表达、推测性措辞、谣言模式以及缺少来源。
- 当预测为非谣言时，优先说明文本是否包含报道或来源线索，以及是否缺少明显的夸张、绝对、推测和谣言模式表达。
- 如果规则没有命中明显线索，则回退为“更接近训练数据中某类文本模式”的解释，避免无依据地编造原因。

## RAG 检索增强解释

为了增强解释模块的可复核性，当前版本加入了轻量级 RAG（Retrieval-Augmented Generation）流程。系统会把训练集文本构建为 TF-IDF 检索库，在生成解释时根据当前输入检索最相似的若干训练样例，并把这些样例的标签分布作为额外上下文。

具体流程如下：

1. 对训练集文本进行与分类模型一致的清洗。
2. 使用 TF-IDF 向量化训练集文本，构建可复用的检索索引。
3. 对输入文本进行向量化，按余弦相似度检索 top-k 相似样例。
4. 在规则解释后补充 RAG 上下文，例如“3 个最近训练样例中有 2 个与当前预测标签一致”。
5. 如果启用 LLM，prompt 中会同时提供规则信号和检索样例，但要求 LLM 只把检索样例作为数据集上下文，而不能把它们当作事实证明。

RAG 模块的作用不是直接判断新闻真假，而是说明当前输入在训练数据空间中更接近哪些已标注样例，从而让模型解释更具体、更容易检查。

## LLM 接入方案

当前代码支持可选接入学校提供的大语言模型接口。为了保证项目可离线运行，规则解释是默认方案；只有当环境变量配置完成后，才会调用 LLM 对规则信号进行自然语言润色。

需要配置的环境变量：

```text
SCHOOL_LLM_API_URL=学校提供的 chat-completions 接口地址
SCHOOL_LLM_API_KEY=学校接口密钥
SCHOOL_LLM_MODEL=模型名称，可选
SCHOOL_LLM_TIMEOUT=超时时间，可选
```

调用原则：

- LLM 只负责把规则信号改写得更自然，不直接替代分类模型。
- Prompt 要求 LLM 不声称文本一定真实或虚假，只解释可观察的文本线索。
- 如果接口未配置或调用失败，系统自动使用规则化解释，保证稳定性。

## 使用方式

单条解释：

```bash
python -m src.explain --text "BREAKING: unconfirmed report says..." --label 1
```

查看详细规则信号和 LLM prompt：

```bash
python -m src.explain --text "BREAKING: unconfirmed report says..." --label 1 --detail
```

生成典型案例文件：

```bash
python -m src.train_baseline
python -m src.build_explainability_cases
```

输出文件：

- `outputs/val_predictions.csv`：验证集预测结果与解释
- `outputs/examples.csv`：前 20 条解释样例
- `outputs/explainability_cases.csv`：5–10 条典型案例，包含输入文本、真实标签、预测结果、判断依据和简要分析

## 局限性分析

规则化解释具有稳定、可复现、易展示的优点，但也存在局限：

- 规则只能识别表层语言线索，不能真正验证事实。
- 一些真实新闻也可能使用 `breaking` 等词，因此规则信号不能单独作为谣言判据。
- 缺少来源线索不代表文本一定为谣言，只说明文本内部没有提供明确核验依据。
- 解释结果依赖分类模型输出；如果模型预测错误，解释只能说明模型倾向，而不能证明标签正确。

因此，报告中应将解释模块定位为“辅助理解模型判断依据”的工具，而不是事实核查系统本身。
